## 🛠 二、本轮修掉的问题

### 2.1 外链缺 `rel="noopener noreferrer"`（安全）

**位置**：`tools/anchors.js`，页脚社交三连 + 移动端菜单社交三连，共 6 条链接、15 处产物。

上游的头部按钮（`nav.agency` / `nav.labs` / `nav.contact`）带了 `rel="noopener noreferrer"`，
社交行没带 —— 同一份产物里两套写法，是遗漏而不是有意为之。

`target="_blank"` 不配 `noopener`，被打开的页面可以通过 `window.opener.location`
把原标签页导航到钓鱼站（反向标签劫持）；不配 `noreferrer` 则会把来源地址一并送出。
现代浏览器对 `_blank` 默认隐含 `noopener`，但这是**生成静态站的模板**，
不能替最终访客假设浏览器版本。

**改法**：新增两个常量，HTML 属性串与 Vue props 对象字面量各一份：

```js
const REL_EXT_HTML = ' rel="noopener noreferrer"';
const REL_EXT_JS = ',rel:"noopener noreferrer"';
```

补丁表的 `find`（上游原文）一个字没动，只改 `replace`。三份产物都覆盖到：
预渲染 HTML 6 处、`engine` chunk 6 处（菜单 3 + 404 页 3）、`page` chunk 3 处。

**回归防护**：`tools/test/anchors.test.js` 新增两条断言 ——
① 打完补丁后 HTML 里不存在任何不含 `noopener` 的 `<a … target="_blank">`；
② 三份产物里 rel 的条数分别精确等于 6 / 6 / 3，且**补丁之前是 0**
（防止将来上游自带了 rel，测试变成空转还显示通过）。

### 2.2 Pages 工作流会掐断正在进行的部署

**位置**：`.github/workflows/pages.yml`

```diff
 concurrency:
   group: pages
-  cancel-in-progress: true
+  cancel-in-progress: false
```

`pages` 这个并发组同时管着构建和 `actions/deploy-pages`。设成 `true` 时，
后一次推送会把**正在写线上的那次部署**取消掉，结果是线上停在更早的版本、
Actions 里留下一条失败记录，而排队的新构建还要从头再来一遍。
GitHub 官方 Pages 模板对此有明确说明，取值就是 `false`。

### 2.3 `__NUXT_DATA__` 写回时不转义尖括号

**位置**：`tools/payload.js` 的 `write()`

`JSON.stringify` 不会转义 `<`。payload 是内嵌在 HTML 里的
`<script type="application/json">`，正文里出现 `</script>` 会当场截断整页。

眼下写进 payload 的只有 `sceneQuality`（枚举）、`soundEnabled`（布尔）、
`sectionColor`（枚举）、`sections`（数字数组），全都过了 `tools/scene.js`
的枚举校验，**当前不可能触发**。但这条路径将来只要加一个自由文本字段就会中招，
而且失败形式是整页白屏，排查成本远高于修复成本。

```js
const json = JSON.stringify(flat).replace(/</g, '\\u003C');
```

`\u003C` 在 JSON 里与 `<` 完全等价，函数内的回读校验照常通过。

### 2.4 构建摘要里的硬编码 `- 1`

**位置**：`tools/build.js`

```js
// 旧
const shell = res.applied.length - 1 - pre.anchors.length - crystals.anchors.length;
```

这个 `-1` 假设 `buildSceneAnchors(scene)` 永远只返回 1 条锚点。加第二条滚动节奏
补丁的那天，摘要就会把外壳的数量报少一条，而且不会有任何报错。
改成按真实分组长度报数：

```js
const shellAnchors = buildAnchors(site);
const sceneAnchors = buildSceneAnchors(scene);
```

`applyAnchors` 有一条对不上就直接抛错，所以几个分组长度之和恒等于
`res.applied.length`，摘要不会失真。

### 2.5 对比度模型漏算了颗粒层（第二轮，正确性）

**位置**：原 `tools/menu.js` 的对比度校验，现已抽到 `tools/grain.js` 的 `worstCaseContrast()`

第一轮的模型把菜单背景算成「底色 + 彩晕 + 网格」三层，唯独把颗粒层当成
「肉眼看不见的装饰，不影响亮度」跳过了。这个假设是错的，而且错的方向很反直觉 ——
**颗粒在亮处提亮、在暗处也提亮，唯独在彩晕峰值上是压暗的**。

原因是噪点纹理的中心灰是 `#404040`（相对亮度 Y ≈ 0.051），而四角彩晕峰值的
亮度在 Y ≈ 0.10 ~ 0.11。把一层 Y ≈ 0.051 的东西以 alpha 混上去，结果只能更暗。

后果是实打实的：`noise: false` 时最坏对比度算出来 7.2，够门槛；
一旦打开颗粒，真实值掉到 **6.1**，低于 `MENU_MIN = 7`，而校验器毫不知情。

修法不是给颗粒补一个平均值修正，而是**三态取最坏**：

```js
// 无颗粒 / 颗粒均值 / 颗粒 +2σ，三种都算，取最低的那个
```

`+2σ` 这一档是必要的 —— 颗粒是随机场，用户看到的不是均值，
而是某个具体像素。取 2σ 覆盖约 97.7% 的像素。
改完之后 `noise` × `grid` 四种开关组合的最坏值全部落在 **7.0:1**。

顺带说明为什么这条归到「修掉的问题」而不是「已知限制」：
它会让一个**已经不达标的配色通过校验**，属于校验器本身失效，不是精度不够。

### 3.2 加载页百分号会横向跳动（字体限制）

打包进来的 `TheSeasons` 斜体**没有 tnum（等宽数字）表**，
所以 `font-variant-numeric:tabular-nums` 和 `font-feature-settings:"tnum" 1`
写了也不生效。实测各数字的内容宽（em，基于桌面 `font-size:378px`）：

```
1 = 0.290   3 = 0.459   5 = 0.435   7 = 0.446   0 = 0.504
2 = 0.559   4 = 0.578   6/8/9 = 0.530
"37" = 0.899   "86" = 1.061   "100" = 1.297
```

后果是数字换位时紧跟其后的 `%` 会左右移动，最坏情况（19 → 20）约 92 px。

**不修的理由**：三种改法都要付出更大的代价 ——
右对齐会让数字随位数增长向左漂、破坏与左栏的对齐线；
把 `%` 挪到容器右缘会拆散「大数字 + 单位」这一组排印关系；
给数字开一个固定宽槽等于人为让 100% 时留白最大，视觉上更别扭。
当前构图里数字是绝对主角，`%` 只是一个 11 px 的下标，跳动在实际观感中很弱。

### 3.3 三份各自实现的 `esc()`

`tools/anchors.js`、`tools/preloader.js`、`tools/blocks.js`、`tools/markup.js`
各有一份 HTML 转义函数。看着像该合并，但四者语义确实不同：

- `anchors.js` / `preloader.js`：值会进**属性**，必须转 `"`，且 `&` 一律转义；
- `blocks.js`：只进文本节点，不需要转 `"`；
- `markup.js`：面向富文本，`&` 用 `(?![a-zA-Z#][a-zA-Z0-9]*;)` 前瞻**保留**
  用户手写的 `&nbsp;` 一类实体。

合并成一个带 flag 的函数只会把「这里到底该不该保留实体」这个判断
从调用点挪进函数里，读代码时反而更难确认。维持现状，此处登记备查。

### 3.5 `dev.js` 构建失败时会多刷新一次页面

`/__dev` 在构建失败时返回 `error:<上一次的构建号>`，与上一次的响应不同，
于是页面刷新一次（刷到的是上一版能用的 `dist/`）。之后就稳定不再刷。
属于开发期的良性行为，不改。

## ⚠️ 四、已知环境限制（不是代码缺陷）

这几条会影响**自动化验证的可信度**，写在这里免得下次又当成 bug 排查：

1. **无 GPU 的环境渲染不出水晶区。**
   `.case-debug` 带 `lg:!hidden`；`CaseHover` 的可见条件是 `c.value > -0.24 && c.value < 1.2`，
   软件渲染下 7 颗水晶的 `y` 恒为 0，watcher 从不触发。SwiftShader 实测 6.2 fps。
   水晶配色只能靠**构建期数值断言**（7 组静止色互不相同、最低亮度、相邻色相间隔）
   加真机目视确认，canvas 回读和截图采样都走不通。

2. **`backdrop-filter` 在软件渲染下 computed 值恒为 `none`**，但 `CSS.supports()` 仍报 true。
   所以端到端测试改为从 **CSSOM 规则文本**里验证声明存在，而不是读 computed style。

3. **伪元素的 `counter()` 在 computed style 中不求值。**
   菜单序号 `01`–`04` 的断言只能比对 content 字面量含 `counter(ns-menu`，
   外加验证 `counter-increment` / `counter-reset` 确实生效。
   两套预设的挂载点还不一样：`ink` 用 `::after` 把序号吊在条目右侧，
   `frost` 改用 `::before` + `display:block` 把序号顶到条目正上方，断言按预设分流。

4. **颗粒的自相关必须在 `device_scale_factor=2` 下量。**（第二轮新增）
   `feTurbulence` 的 `baseFrequency` 是相对 SVG 用户单位算的，从 CSS 像素到设备像素
   中间还有一次缩放。1× 下量出来的 lag-1 会系统性偏低，照着它调 `freq`
   会把颗粒调得过粗。`tools/grain.js` 的标定值（`freq 0.70` → lag1 0.618 / lag2 0.020）
   一律以 2× 为准，改标定参数时必须同步改量测脚本的 DPR。

另有一条与渲染无关：截图采样一律取 **21 × 21 像素的众数色**，
单点采样会被字体抗锯齿边缘误导。第二轮再加一条 —— 颗粒层是半透明盖在彩晕上的，
九点探针会撞上文字，所以颗粒强度改用「开 / 关颗粒两张图做差分」隔离，不做绝对采样。
